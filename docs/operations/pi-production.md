# Production Pi appliance

The appliance serves the dashboard on loopback TLS at port 5173 and the desktop API proxy at port 8443. The proxy authenticates itself to Gunicorn on loopback port 8010. The phone tunnel uses that same backend with a separate credential, hostname and machine-route allowlist. The development backend uses port 8000. The dedicated local owner retains automatic desktop entry. Any process with access to the local desktop can exercise its authority.

## Stage the candidate

1. Use a root-owned release directory under /opt/health03. Include backend, contracts, infra, scripts, pyproject.toml and uv.lock. Create the locked Linux environment **at its final path** with `uv sync --frozen --no-dev`. Build the frontend with Node 24 and pnpm 10 using `pnpm install --frozen-lockfile` and `VITE_LOCAL_DESKTOP=1 pnpm build` in frontend. Include frontend/dist. Provide Node at /usr/bin/node on the Pi. Keep the previous release directory. Point /opt/health03/current at the staged release during cutover.
2. Provision local PostgreSQL and the scoped OpenBao agent socket. On an existing appliance keep the database, source namespace, device credentials, signing secret, blob set and original OpenBao keys together. Confirm the blob path and database selection before cutover. A new empty database, blob directory or key service cannot serve historical records. With backups disabled, plan any data-moving or irreversible migration separately.
3. Create the database login roles using infra/postgresql/roles.sql as the database administrator in the intended database. Run migrations as its schema owner health03-migrate using the staged environment. Apply roles.sql and then audit-privileges.sql in that same database after migrations. Runtime units use local peer authentication with their own service names.
4. Prepare /etc/health03/runtime.env from the production settings in the root .env.example with actual deployment values. For the revision use the full commit of the staged, clean release. Supply its independently approved release gate, readable by the service accounts. Follow docs/security/release-operation.md for approval. The dated backend-local manifest does not authorize a release.
5. Supply root-owned mode-0600 files in /etc/health03/credentials for django-secret, smtp-password, tunnel-origin-secret, desktop-proxy-secret, localhost.key and localhost.pem. Use a separate randomly generated desktop proxy secret. The local browser must trust the localhost certificate. Configure the edge to **replace** X-Health03-Origin with the tunnel-origin-secret and bypass cache on the phone hostname. Verify existing device registrations before issuing any new handoff.
6. On cutover stop and disable the old local web/worker services and the old desktop user's dashboard/proxy units. Once the database and existing ciphertext are available in their production locations, run `sudo bash /opt/health03/current/scripts/install_pi_services.sh`. It checks the gate and migrations, installs the units, and sets shared group access on the encrypted store. On a Pi already provisioned for unattended unlock it reuses /etc/health03/unattended/share-1, share-2 and server-ca.crt. Keep that directory root-only. Other key-service unlock arrangements can remain independently managed.
7. With the production services healthy, install ingress with `sudo bash /opt/health03/current/scripts/install_mobile_tunnel.sh TUNNEL_UUID CREDENTIAL_JSON`. Use the existing tunnel and matching DNS mapping. The installer checks the production listener before switching the connector.

## Verify and operate

In an isolated Linux test database with the scoped Transit agent active, set PGDATABASE and PGUSER for a test user with CREATEDB, then run `make pi-acceptance`. The Pi intake regressions run real concurrent requests, database rollback, corrections, deletion and historical index repair. Confirm the full suite reports no skipped real-KMS tests.

Exercise the installed services on a synthetic appliance before admitting owner data. Open the trusted localhost dashboard and confirm automatic entry. Submit a synthetic phone batch, repeat the same batch, poll until the item has an accepted receipt, and read the corresponding dashboard value. Confirm both service users produce group-readable mode-0640 ciphertext under the setgid blob directory. Verify a forbidden dashboard path on the phone host returns 404 and unauthenticated phone config returns 401. Start the retention service and check its result. Reboot and repeat the upload and read with the same device credential. Verify the external HTTPS path separately against the intended tunnel before release.

Backups are disabled by default. On-device unseal shares support unattended restarts and give a privileged holder of the Pi access to unlocking material. Loss of the device or its keys can permanently lose the records. Changing either policy requires an owner decision.

For a code-only rollback, close ingress, restore the previous compatible release and its matching configuration, and recheck the processed receipt and dashboard. Keep the current database, revocations and tombstones. If the schema is incompatible, leave ingress closed.
