# Operator security procedures

These commands are implementation entry points. Production release requires the end-of-build evidence; an installed command is not a passed recovery drill.

- **Sealed key service:** verify host, server/client certificates and audit state; explicitly unseal with two separately held shares. Never configure automatic unseal from files stored beside the database. Synthetic helper scripts are not production custody.
- **Lost phone:** revoke its registration in the owner session, publish the revocation outbox, and reconnect the recovered/replacement installation. Its upload queue remains encrypted on the phone. A lost refresh response requires reconnect, not token replay.
- **Stolen session:** revoke session security state, rotate account security epoch, revoke native families if credentials may be exposed. Reset via the verified mail flow and require ordinary password login.
- **Compromise:** run `health03_incident_lock`; stop public ingress; preserve minimal audit evidence. Rebuild on a clean trusted runtime, revoke certificate identities/tokens, renew credentials and perform a verified restore. KEK rotation alone is not recovery from an authorized-process compromise.
- **Owner recovery:** operate over the management boundary; establish identity outside an unverified email claim; revoke sessions/families and all doctor grants before recovery. Do not create a second owner or a passwordless bypass.
- **Late/failed backup:** inspect `health03_ops_status`, repository/TLS/credential availability and ledger backlog. Run `health03_backup` only after ledger acknowledgement. Incomplete sets cannot be selected as complete backups.
- **Restore:** use `HEALTH03_ENV=restore`, a `health03_restore_*` database, a new `/var/lib/health03-restore/<candidate>` directory and a separate TLS OpenBao instance on loopback port 18200. Supply a current ledger export and independently obtained head, the recovery kit, isolated initial token and two share files. Run `health03_restore_verify --environment=restore --backup-set=<set-uuid>`. It never enables web/tunnel ingress. It replays reductions, revokes restored credentials/grants, verifies ciphertext, restores/unseals the separate key service and decrypts the synthetic canary and retained envelopes. Record measured RPO/RTO, including missed targets.
- **Deleted data in a candidate:** keep it locked; reconcile ledger completeness and source tombstones. Never release a candidate solely because its database starts.
- **Bad release:** switch code to the last known-good release only if schema compatibility is established. Otherwise use the restore procedure. Never roll back the independent deletion ledger, revocations or permission state.
- **Certificates/keys:** monitor 30-day certificate warnings hourly. Use the offline CA and scoped operator identity for renewal; revoke old identities/tokens. Acquire maintenance lock 3103005 for rotation/rewrap, retention and backup coordination. Retain KEK versions required by any live envelope or retained backup. Do not rotate the identity HMAC key until dual-index/tombstone reindexing exists.

Backup and ledger targets are owner-controlled infrastructure, not a paid-service requirement. No target or off-device durability is claimed until configured. The backup boundary must run rest-server with append-only protection and verified TLS. Retention/pruning uses a separate operator identity; the Pi's append credential cannot prune history. Configure SSH forced-command append access with `restrict,command=".../ledger_receiver.py"`, no shell, forwarding or general filesystem operations.

Operational notices contain no medical data. Monitoring currently reports locally; no email/notification recipient is assumed or contacted. Daily backup/ledger health, weekly access review, monthly dependency maintenance, annual clinical KEK rotation and quarterly decrypting restore are tracked release obligations.
